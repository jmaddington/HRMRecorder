A minimal Flask receiver.

One file — about 300 lines, heavily commented: Flask + SQLite + a static Bearer token, implementing the complete Protocol v1 conformance checklist. Download hrm_receiver.py and read along.

This is a starting point for receiving your own health data on your own server — deliberately small so you can read all of it, not hardened production code. Two things it does not do for you: TLS (put a reverse proxy like Caddy or nginx in front — the app refuses plain http:// base URLs, so this is not optional) and multi-user accounts (one token, one account — the token is the account).

Run it

# In a fresh directory:
uv venv venv && source venv/bin/activate   # or python3 -m venv venv
uv pip install flask                        # or: pip install flask

export HRM_TOKEN="pick-a-long-random-string"
python hrm_receiver.py                      # or: flask --app hrm_receiver run

Then in the app: Settings → Server Sync → enter your server's HTTPS base URL and paste the same token. The "Test connection" button calls GET /ping, sees "mode": "token", and knows to use the pasted token as a Bearer credential.

Discovery: GET /ping

The only unauthenticated endpoint. It tells the app the protocol version, the biggest samples batch we accept, and how to authenticate: 

@app.get("/ping")
def ping():
    return jsonify({
        "ok": True,
        "protocol": 1,
        "limits": {"max_samples_per_request": MAX_SAMPLES},
        "auth": {"mode": "token"},
    })

Auth: one token, checked everywhere else

A before_request hook rejects anything but /ping unless the Bearer token matches. Note hmac.compare_digest rather than == — a constant-time comparison avoids leaking token prefixes through response timing: 

@app.before_request
def check_auth():
    if request.path.rstrip("/").endswith("/ping") and request.method == "GET":
        return None
    header = request.headers.get("Authorization", "")
    supplied = header[len("Bearer "):] if header.startswith("Bearer ") else ""
    if not hmac.compare_digest(supplied.encode(), TOKEN.encode()):
        return err(401, "unauthorized", "Bearer token required")

Devices & sessions: the COALESCE upsert

Strap identity (manufacturer, model, firmware…) arrives on the phone as separate asynchronous Bluetooth reads, so the app sends partial rows that fill in over time. The rule: an incoming non-null field wins; an incoming null or blank never clobbers a stored value. SQLite's ON CONFLICT … DO UPDATE with COALESCE expresses it directly: 

ON CONFLICT(client_device_id) DO UPDATE SET
  name          = COALESCE(excluded.name, name),
  manufacturer  = COALESCE(excluded.manufacturer, manufacturer),
  ...
  -- first_seen is historical fact: first write wins.
  first_seen    = COALESCE(first_seen, excluded.first_seen)

(excluded.x is the incoming value; bare x is what's stored. Blank strings are normalized to None before binding so they count as null.) Sessions use the same pattern, with one extra rule — ended_at may go null → value exactly once, and never back. A re-sent stale "still recording" snapshot must not reopen a closed session: 

started_at = COALESCE(excluded.started_at, started_at),  -- incoming wins
ended_at   = COALESCE(ended_at, excluded.ended_at),       -- stored wins

Samples: dedupe, forward references, and the cursor

Three invariants make re-sending always safe for the app:

  1. Silent dedupe. The table's primary key is (client_session_id, client_sample_id) — the protocol's idempotency identity — and inserts use INSERT OR IGNORE. A duplicate is counted, not rejected; the response says {"accepted": 0, "duplicates": 3, ...} and never a 409.
  2. Forward references. A sample may arrive before its session or device row (the app batches independently). The receiver stubs the parent rows with INSERT OR IGNORE; later upserts upgrade the stubs via COALESCE.
  3. An honest cursor. max_client_sample_id is computed from the database after commit — the largest id durably stored across the request's sessions — never echoed from the batch. The app trusts this number as its resume point, so guessing here loses data.

Oversized batches get the protocol's exact over-cap shape, which the app reacts to by halving and retrying: 

if len(items) > max_items:
    return err(413, "batch_too_large", max=max_items)

State recovery: GET /sessions/<id>

After a reinstall (or if you restore the server from an old backup), the app asks what the server already has and repairs its cursor. An unknown session is a normal answer — {"known": false} with HTTP 200, because to the app a 404 means "wrong base URL".

Try it with curl

The same round-trip the app performs (against a local run):

B=http://127.0.0.1:8000
T="Authorization: Bearer pick-a-long-random-string"

curl $B/ping
# {"auth":{"mode":"token"},"limits":{"max_samples_per_request":1000},"ok":true,"protocol":1}

curl -H "$T" -H 'Content-Type: application/json' -X POST $B/sessions \
  -d '{"items":[{"client_session_id":"s1","started_at":1752314400.0,"ended_at":null}]}'
# {"accepted":1}

curl -H "$T" -H 'Content-Type: application/json' -X POST $B/samples \
  -d '{"items":[{"client_session_id":"s1","client_sample_id":101,
       "ts":1752314401.25,"bpm":62,"rr_ms":"968;962","contact":1}]}'
# {"accepted":1,"duplicates":0,"max_client_sample_id":101}

# Re-send the identical batch — idempotency in action:
# {"accepted":0,"duplicates":1,"max_client_sample_id":101}

curl -H "$T" $B/sessions/s1
# {"ended_at":null,"known":true,"max_client_sample_id":101,"sample_count":1}

Where to go from here

  • Full contract: the API reference and the normative SYNC_PROTOCOL.md.
  • Cross-check your own implementation against the repo's stdlib mock server — python3 mock_server.py --selftest exercises the tricky invariants, including the OAuth 2.1 flow this example skips.
  • Hardening ideas, in rough order: TLS via reverse proxy (required), a WSGI server (gunicorn/waitress), request-size limits, backups of the SQLite file, and rate limiting.
