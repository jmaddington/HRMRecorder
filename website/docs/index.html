How the app records, what the export contains, where your data lives, and how to receive it on a server you run.

Getting started

  1. Pair a strap. Wear any Bluetooth heart-rate sensor that speaks the standard Heart Rate Service (0x180D) — Garmin HRM-Pro+, Polar H10, Wahoo TICKR, and most chest straps. Open the app, allow Bluetooth, and pick your strap from the list. The app remembers it and reconnects automatically from then on.
  2. Record. Tap Start Recording. Every reading the strap sends — about one per second — is written to disk immediately. Recording continues with the screen off and the app in the background; if the strap drops out, the session resumes when it reconnects.
  3. Export. Export one session, or everything, as CSV from the sessions list. The file opens in the iOS share sheet — save to Files, AirDrop it, mail it.

The CSV format

One row per reading from the strap — roughly one per second, and a single row can carry several R-R intervals. Text fields are RFC-4180 quoted, so the file opens cleanly in Excel, Numbers, pandas, and R. Columns, in order:

CSV export columns and their meanings
ColumnMeaning
timestamp_isoSample time as an ISO-8601 string.
unix_secondsSample time as Unix epoch seconds, with sub-second precision — the authoritative timestamp.
session_idThe recording session this sample belongs to.
device_name, manufacturer, model, firmware, body_locationSensor identity, denormalized onto every row so each CSV is self-describing. Resolved from the per-sample strap when known, falling back to the session's primary strap.
bpmHeart rate reported by the strap, beats per minute.
rr_msR-R intervals in milliseconds, semicolon-joined (e.g. "812;806") — one Bluetooth packet can carry several intervals. The cell is double-quoted so the embedded ; stays one cell even in locales that use ; as the list separator. Empty if the strap didn't send R-R data.
sensor_contactSkin-contact status: 1 good, 0 poor, blank when the strap doesn't report it.
energy_kjEnergy expended in kilojoules, when the strap reports it.
device_idBluetooth UUID of the strap that produced this specific reading — sessions can span multiple straps. Blank for rows recorded before multi-strap support.
device_strap_nameAdvertised name of that per-sample strap.

Where your data lives

Everything is stored on your device in a single SQLite file inside the app's sandbox: Application Support/hrm.sqlite3 (the path is shown at the bottom of the app). WAL mode is enabled so writes are durable in real time. The full schema — sessions, samples, devices — is published in the repository README, so you can bring your own tools to the raw database, not just the CSV.

Self-hosted server sync

Optionally, the app can push everything it records to a server — your server. There is no hosted service and no default destination: hosting other people's health data carries obligations we'd rather not meet halfway, so the app ships tools instead — an open protocol and working example code. You point it at a base URL you control, and it uploads devices, sessions, and every sample, incrementally and idempotently.

  • HTTPS only. The app refuses plain http:// base URLs, no exceptions.
  • Auth is your choice. A static Bearer token you paste into the app's settings, or full OAuth 2.1 with PKCE if your server advertises it. Tokens live in the iOS Keychain.
  • Safe to re-send. The protocol is idempotent and resumable — crashes, reinstalls, and flaky networks never duplicate or corrupt data, and sync never deletes anything local.
