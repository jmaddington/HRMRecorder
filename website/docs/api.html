Sync API.

Server Sync Protocol v1 — implemented and shipping in the app. This page is a reference rendering of the normative spec: SYNC_PROTOCOL.md. The stdlib mock server (run it with --selftest) is the executable conformance reference.

HRM Recorder is not tied to any one server. The user supplies a base URL and authenticates; the app then pushes its recorded data using the protocol below. Implement it and the app syncs to your server with no app changes. Design goals: anyone can implement the server side (plain HTTPS + JSON), writes are idempotent and resumable, sync is incremental, data is transferred at full fidelity (every ~1 Hz sample, R-R intervals, per-strap attribution), and a sync never deletes anything on the phone — the local SQLite database stays the source of truth.

Transport & conventions

Transport and protocol conventions

TransportHTTPS only. Plaintext HTTP is rejected by the app, no exceptions.

For a configured base B, a conformant server exposes:

GET   B/ping                              # unauthenticated discovery
POST  B/devices
POST  B/sessions
POST  B/samples
GET   B/sessions/{client_session_id}

ping is the only unauthenticated endpoint; it carries no user data and exists so the app can discover reachability, protocol version, batch limits, and how to authenticate before it has a token.

Authentication

Every data request carries Authorization: Bearer. How the app obtains the token depends on what the server advertises in GET ping under auth:

OAuth 2.1 (preferred)

If ping.auth.mode == "oauth", the server provides auth.oauth_metadata_url — an absolute URL to RFC 8414 authorization-server metadata. The app then performs standard OAuth 2.1:

  • RFC 8414 metadata discovery at oauth_metadata_url.
  • RFC 7591 dynamic client registration — the app is a public client; no pre-registration or operator-side app config required.
  • Authorization Code + PKCE (S256) in an in-app system web-auth session; the custom scheme hrmrecorder://oauth-callback returns the code.
  • Token exchange yields an access token plus a refresh token — the refresh token is what lets the background uploader keep working unattended; the user signs in once.
  • On 401, the app refreshes; if refresh fails it surfaces "sign in again" (recording is never affected).
  • Servers must enforce an exact redirect-URI match; short-lived access tokens with rotating refresh tokens are recommended.

This can reuse a server's existing OAuth 2.1 authorization server — no HR-specific OAuth endpoint is required. Tokens must carry write access for ingest and read access for the read endpoints.

Static Bearer token (fallback)

If ping.auth.mode == "token" (or ping is unreachable or omits auth), the app uses a static opaque token the user pastes into Settings, issued out-of-band from your server's own settings UI. This keeps the minimum server bar low: a DIY server that only checks a shared secret is fully conformant.

Either way the token is opaque to the app and stored in the iOS Keychain, never in plist-backed preferences.

Identifiers

Client-generated identifiers
NameTypeOriginStability

All three are client-generated. The server treats them as opaque natural keys scoped to the authenticated account, assigns its own primary keys, and must never require the client to know server-side keys. There are no account identifiers on the wire — the token is the account.

Endpoints

Writes are batch-shaped ({"items":[...]}) so one endpoint serves one or many items. All writes are idempotent.

GET ping — unauthenticated discovery

{
  "ok": true,
  "protocol": 1,
  "limits": { "max_samples_per_request": 1000 },
  "auth": {
    "mode": "oauth",
    "oauth_metadata_url": "https://dash.example.com/.well-known/oauth-authorization-server"
  }
}

auth.mode is "oauth" or "token"; for "token", oauth_metadata_url is omitted. The app's "Test connection" button calls this, then (if it has a token) an authenticated probe.

POST devices — upsert strap identities

Request: {"items":[Device, ...]}, at most 200 items.

{
  "items": [
    {
      "client_device_id": "6E7A1C0B-3C9A-4F2D-9E76-2B1F0A9C4D11",
      "name": "HRM-Pro+",
      "manufacturer": "Garmin",
      "model": null,
      "firmware": "5.10",
      "body_location": "Chest",
      "first_seen": 1747668000.0
    }
  ]
}

Response: 200 {"accepted": 1}.

COALESCE semantics: a null/blank field must not overwrite a stored non-null value. Device details arrive on the phone as separate asynchronous Bluetooth reads, so partial rows trickle in and accumulate.

POST sessions — upsert sessions

Request: {"items":[Session, ...]}, at most 200 items.

{
  "items": [
    {
      "client_session_id": "20260519T143012Z-a3f",
      "started_at": 1747668612.4,
      "ended_at": null,
      "device_name": "HRM-Pro+",
      "manufacturer": "Garmin",
      "model": "HRM-Pro Plus",
      "firmware": "5.10",
      "body_location": "Chest"
    }
  ]
}

Response: 200 {"accepted": 1}. Same COALESCE rules; additionally ended_at may transition null → value (the session closed) but never back.

POST samples — append samples

Request: {"items":[Sample, ...]}, at most max_samples_per_request items. 

{
  "items": [
    {
      "client_session_id": "20260519T143012Z-a3f",
      "client_sample_id": 84211,
      "client_device_id": "6E7A1C0B-3C9A-4F2D-9E76-2B1F0A9C4D11",
      "ts": 1747668613.25,
      "bpm": 62,
      "rr_ms": "968;962",
      "contact": 1,
      "energy_kj": null
    }
  ]
}

Response:

{ "accepted": 1000, "duplicates": 0, "max_client_sample_id": 84211 }
  • Dedupe on (account, client_session_id, client_sample_id); duplicates are ignored silently — never a 409.
  • Samples whose session/device rows have not arrived yet are still accepted (forward references).
  • max_client_sample_id is the largest id durably stored for this account across the request's sessions — the app's cursor.
  • Over-cap requests get 413 {"error":{"code":"batch_too_large","max":N}}.

GET sessions/{client_session_id} — state recovery

Cursor/state recovery after a reinstall or a server restore-from-backup.

{ "known": true, "ended_at": 1747668000.0, "sample_count": 6588, "max_client_sample_id": 84211 }

An unknown session returns {"known": false} with HTTP 200 — absence is a normal answer, not an error.

Resources

Field nullability matches the app's SQLite schema — null wherever the strap did not report a value. Fields marked ? are nullable/optional.

Resource field definitions
ResourceFields
Device client_device_id, name?, manufacturer?, model?, firmware?, body_location?, first_seen (epoch)
Session client_session_id, started_at (epoch), ended_at? (epoch; null while recording), device_name?, manufacturer?, model?, firmware?, body_location?
Sample client_session_id, client_sample_id (int64), client_device_id?, ts (epoch, sub-second), bpm (int), rr_ms? (semicolon-joined ms, verbatim, e.g. "812;806"), contact? (1 good / 0 poor / null), energy_kj? (int)

Batching & limits

  • Default sample-batch ceiling is 1000; a server may lower it via ping.limits.max_samples_per_request, and the app honors it.
  • An over-cap body gets 413 {"error":{"code":"batch_too_large","max":N}}; the app halves the batch and retries.
  • The app sends batches in ascending client_sample_id and advances its cursor only after a 2xx.

Idempotency & incremental sync

The app keeps one integer cursor — the highest acknowledged client_sample_id. The client algorithm: 

on trigger (session end, app foreground/background, retry timer):
  ensure valid token (OAuth refresh if needed) — else surface, stop
  POST devices   { changed devices }
  POST sessions  { sessions touched since last sync }
  loop:
    batch = local samples WHERE id > cursor ORDER BY id LIMIT N
    if empty: break
    resp = POST samples { batch }
    cursor = max(cursor, resp.max_client_sample_id)
  persist cursor

Cursor repair (reinstall, lost local state, server restored from an old backup): the app calls GET sessions/{id} and sets cursor = min(local, server.max_client_sample_id), so anything the server lacks is re-sent. Because writes are idempotent, over-sending is always safe.

Errors

Non-2xx responses carry a JSON body: {"error":{"code":"...","message":"..."}}.

A sync failure never affects recording and never deletes local data.

Minimum conformance checklist

A conformant server MUST:

  1. Serve GET ping unauthenticated with protocol, limits, and auth.
  2. Authenticate every data request via Authorization: Bearer.
  3. Either advertise OAuth 2.1 (RFC 8414 metadata + RFC 7591 + PKCE) or accept a static Bearer token — at least one.
  4. Implement devices, sessions, samples, sessions/{id}.
  5. Treat (account, client_session_id, client_sample_id) as the sample identity; ignore duplicates without error.
  6. Apply COALESCE (non-null-wins) upsert to device/session identity fields.
  7. Return an accurate max_client_sample_id; accept samples whose session/device rows have not arrived yet; never require server-side keys.
